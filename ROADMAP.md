## Vision

TheoDB é o PostgreSQL com superpoderes de IA e analytics — **open-source e rodando em qualquer
lugar**. O AlloyDB Omni provou que existe demanda por "PostgreSQL + IA + analytics empacotados,
rodando em qualquer lugar" — mas é proprietário e pago ($40/vCPU/mês). O TheoDB ocupa exatamente
essa lacuna sendo **100% open-source**, sem licença por vCPU e sem lock-in, **compondo** o engine
maduro do PostgreSQL com um conjunto curado de extensões permissivas (com destaque para um pgvector
customizado) — **sem reinventar o engine**.

## Problem

**Root problem:** Equipes que querem PostgreSQL com IA e analytics escolhem hoje entre opções ruins —
Postgres vanilla + montar extensões à mão (integração frágil, sem tuning conjunto), AlloyDB Omni
(proprietário, $40/vCPU/mês, fechado, sem auditoria), AlloyDB managed (lock-in GCP, não roda
on-prem/edge), ou bancos vetoriais dedicados (mais um sistema, ETL, sem SQL unificado). Existe um
vácuo: ninguém oferece o "AlloyDB Omni open-source".

**Whose pain:** Devs de aplicações gen-AI que querem embeddings + vector search no mesmo banco dos
dados operacionais; times de plataforma/DBA pagando licença por vCPU; ambientes on-prem/edge/regulados
que precisam rodar fora da nuvem com código auditável.

## Users

- **Primary:** Dev de aplicação gen-AI (RAG/agentes) — externo, comunidade aberta — quer embeddings +
  vector search no mesmo banco dos dados operacionais, via SQL, sem ETL.
- **Secondary:** Engenheiro de plataforma / DBA (on-prem/multicloud); times com requisito de
  soberania/edge (regulado, air-gap); empresas fugindo de lock-in/custo; contribuidores OSS.

## Scope

### In scope (V1 — required to call this project alive)

- **P1 — Compatibilidade + empacotamento:** distribuição PostgreSQL-compatível (PostgreSQL 17) em
  imagem container, 100% wire-compatible, com extensões pré-instaladas e tunadas em conjunto.
- **P2 — Vetorial / IA (pilar killer):** pgvector + pgvectorscale com índice ANN avançado
  (StreamingDiskANN) + geração de embeddings via SQL.
- **P8 — Deploy mínimo:** imagem container oficial (operador K8s fica para depois).
- **P9 — Migração mínima:** import/export padrão, caminho de entrada a partir do PostgreSQL vanilla.
- **Licença + due-diligence das dependências do MVP (gate de release).**

### Explicitly out of scope

- **Columnar/HTAP completo, HA/DR completo, read pools, operador K8s/RPM avançado, NL→SQL,
  observabilidade/auto-tuning, MCP/integrações** — *why excluded:* são pilares posteriores; o MVP é
  estreito (M0→M2) para não abrir pilar novo antes de fechar o anterior (PRD §13/§14, Regra 2).
- **Engine novo ou fork divergente do PostgreSQL; serviço gerenciado de nuvem na v1; paridade de
  performance com o engine proprietário do Google** — *why excluded:* a tese é compor sobre o Postgres
  (Regra 9); managed fica para pós-tração com a porta aberta via operador K8s (D7); competimos em
  abertura/custo, não prometemos paridade (PRD §3).

> Items in this list are off-limits for V1. To reconsider, write a new roadmap revision — do not silently expand scope.

## Constraints

| Category | Constraint |
|---|---|
| Stack | PostgreSQL 17 (MVP) → 18; compor sobre o engine + extensões maduras; **sem fork do engine** (extensões podem ser forkadas sob a Política de Fork D3: upstream-first, gatilho por benchmark, diff mínimo, CI de rebase, saída quando upstream alcançar). |
| Compliance / legal | Licença **Apache 2.0** (D1) → **dependências AGPL proibidas** na distribuição; só Apache 2.0 / MIT / BSD / PostgreSQL License. Due-diligence é **gate de release** (loop-check-licence). DCO sem CLA (D6). Telemetria opt-in/anônima/off por padrão (D4). |
| Deadline | Nenhum prazo fixo — entrega orientada por marcos e evidência, não por data. |
| Team | usetheo (mantenedores core) + comunidade OSS via DCO. |
| Runtime target | Roda em qualquer lugar com a mesma imagem: laptop · on-prem · edge · qualquer nuvem · K8s · bare metal. Base: Linux + SSD. |
| Budget (infra, tooling) | OSS-first; sem custo de licença de terceiros (constraint de licença já barra deps comerciais/AGPL). |

## Success criteria

**V1 ship criterion (measurable):** A imagem container oficial roda PostgreSQL 17 com
pgvector + pgvectorscale, aceita conexão via protocolo wire de qualquer driver Postgres **sem
alteração de cliente**, e executa vector search end-to-end (tipo vetorial + operadores `<=>` + índice
ANN avançado); **100% dos testes de regressão do PostgreSQL 17 upstream passam** na distribuição; e a
**due-diligence de licença está limpa (zero AGPL no pacote)**. Metas de performance são metas de
design com benchmark reproduzível em `docs/benchmarks/` — nunca claim sem evidência (`public-copy`).

> Example shape: "100 req/s sustained P95 < 200ms across 3 providers, with zero retries hidden from caller", NOT "feels fast".

**North-star metric (tracked post-launch):** **Casos de migração saindo de AlloyDB pago → TheoDB** —
a prova de que o "AlloyDB OSS" tem tração real e ocupa o vácuo de mercado. Métricas de apoio:
pulls/downloads da imagem, contribuidores externos, % de testes de compat Postgres passando.

> The number that, when it moves, the team knows the project is winning. Differs from ship criterion — ship is "alive", north-star is "winning".

### M0 — [ ] Walking skeleton

**Objective:** Empacotar a fatia mais fina end-to-end que prova a arquitetura "PostgreSQL + extensões,
sem fork": uma imagem container TheoDB com PostgreSQL 17 + pgvector pré-instalado que aceita conexão
wire e executa vector search.

**Definition of done (all must hold):**

- [ ] A imagem container builda e sobe um PostgreSQL 17 que aceita conexão via protocolo wire de um cliente padrão (psql/driver) sem alteração.
- [ ] `CREATE EXTENSION vector;` funciona e uma query de similaridade (`<=>`) retorna resultado correto end-to-end num smoke test automatizado.
- [ ] ADR "sem fork do engine PostgreSQL" registrado em `docs/adr/` (promove a decisão de §6 do PRD); decisões D1–D7 referenciadas como ADRs `0001..0007` a formalizar.

**Dependencies:** none (this is the foundation).

**Top risks:**

1. Tuning conjunto de extensões pré-instaladas pode conflitar com a major do Postgres escolhida.
2. Definir o smoke test de wire-compat mínimo sem antecipar a suíte de compatibilidade completa (escopo de M1).

### M1 — [ ] Core + empacotamento

**Objective:** Distribuição PostgreSQL-compatível completa em imagem container, com extensões
pré-instaladas e a suíte de compatibilidade do upstream passando.

**Definition of done:**

- [ ] 100% dos testes de regressão do PostgreSQL 17 upstream passam na distribuição.
- [ ] Extensões do MVP pré-instaladas e habilitáveis via `CREATE EXTENSION`, com tuning conjunto documentado.
- [ ] Due-diligence de licença das deps do core executada (`loop-check-licence`); zero AGPL no pacote.

**Dependencies:** M0.

**Top risks:**

1. Divergência entre versões de extensões e o major do Postgres a cada bump.
2. Custo de manter a suíte de compatibilidade verde continuamente.

---

### M2 — [ ] Vetorial / IA (pilar killer) — MVP

**Objective:** pgvector customizado (`pgvector` + `pgvectorscale`) com índice ANN avançado
(StreamingDiskANN) + geração de embeddings via SQL — o diferencial técnico do TheoDB.

**Definition of done:**

- [ ] Índice ANN além do HNSW disponível (pgvectorscale StreamingDiskANN), com recall medido em dataset de referência e **benchmark reproduzível publicado** em `docs/benchmarks/`.
- [ ] Função SQL para gerar embeddings a partir de modelo configurável (local e/ou remoto).
- [ ] Política de Fork (D3) honrada: qualquer patch em pgvector/pgvectorscale tem benchmark de gatilho + diff mínimo + CI de rebase — ou permanece upstream as-is.

**Dependencies:** M1.

**Top risks:**

1. Manutenção de fork divergindo do upstream (mitigado pela Política de Fork D3).
2. Benchmark de recall/latência não atingir meta competitiva — honestidade: marcar `UNBENCHMARKED` até haver evidência.

---

### M3 — [ ] Migração mínima

**Objective:** Caminho de entrada a partir do PostgreSQL vanilla via import/export padrão.

**Definition of done:**

- [ ] Import/export padrão (`pg_dump`/`pg_restore`) documentado e testado contra um Postgres vanilla.
- [ ] Migração de um banco vanilla com tabela vetorial preserva dados e índices num smoke test.
- [ ] Guia de migração mínima publicado.

**Dependencies:** M2.

**Top risks:**

1. Incompatibilidades de versão de extensão entre origem e destino.
2. Tamanho de dataset tornando o import inviável sem streaming.

---

### M4 — [ ] Operação básica (HA + backup)

**Objective:** Alta disponibilidade com failover automático (primary + standby) e backup contínuo + PITR.

**Definition of done:**

- [ ] Primary com standby e failover automático sob tempo-alvo medido (Patroni-based).
- [ ] Backup contínuo + PITR e backups agendados funcionando (pgBackRest-based), com restore validado.
- [ ] Due-diligence de licença de Patroni/pgBackRest confirmada permissiva (PRD §11 — "a confirmar").

**Dependencies:** M1 (core estável). M2 não é bloqueante.

**Top risks:**

1. Split-brain em failover mal configurado.
2. Janela de RPO/RTO não atingir a meta de design.

---

### M5 — [ ] Deploy em produção (operador K8s + RPM/bare metal)

**Objective:** Operador Kubernetes e orquestrador para RPM/bare metal — a mesma imagem do laptop ao
bare metal regulado.

**Definition of done:**

- [ ] Operador Kubernetes provisiona um cluster TheoDB (primary + standby) declarativamente.
- [ ] Orquestrador RPM/bare metal sobe a mesma distribuição sem rebuild.
- [ ] Smoke de portabilidade: a mesma imagem roda em laptop e em alvo bare metal.

**Dependencies:** M4 (HA é o que o operador orquestra).

**Top risks:**

1. Diferenças de ambiente (GKE/EKS/AKS/OpenShift) quebrando o operador.
2. Complexidade do operador virar fardo de manutenção (KISS).

---

### M6 — [ ] Analytics colunar / HTAP

**Objective:** Camada de armazenamento colunar (DuckDB-powered, `pg_mooncake` MIT) para analytics
rápido sobre dados transacionais vivos, com escolha de plano row vs colunar.

**Definition of done:**

- [ ] Armazenamento colunar (`pg_mooncake`) habilitado para tabelas/colunas selecionadas, com query analítica medida vs row-store.
- [ ] Escolha de plano row vs colunar pelo planner documentada.
- [ ] Honestidade documentada: é columnar lakehouse (DuckDB+Iceberg), **não** in-memory como o AlloyDB (D2).

**Dependencies:** M1.

**Top risks:**

1. `pg_mooncake` não suportar o major do Postgres alvo.
2. Overhead de sincronização row↔colunar.

---

### M7 — [ ] IA avançada

**Objective:** Filtered vector search, hybrid search + reranking, e NL → SQL com views parametrizadas
seguras.

**Definition of done:**

- [ ] Filtered vector search integrado ao planner, com benchmark.
- [ ] Hybrid search (texto + semântico) + reranking (RRF) com recall medido (ex.: BEIR).
- [ ] NL → SQL com guarda contra prompt-injection (views parametrizadas seguras); **alternativa permissiva** identificada para full-text BM25 (paradedb `pg_search` é AGPL → barrado).

**Dependencies:** M2.

**Top risks:**

1. Sem peça permissiva madura para BM25 full-text (paradedb `pg_search` é AGPL).
2. Prompt-injection no NL→SQL — segurança é gate, não opcional.

---

### M8 — [ ] Escala, observabilidade & ecossistema/DX

**Objective:** Read pools com load-balancing, index advisor, autovacuum adaptativo, métricas
OTel/Prometheus + MCP server, integrações (LangChain/LlamaIndex), UI de administração e migração a
partir de AlloyDB. *(Merge de README M8 — Escala & observabilidade — com README M9 — Ecossistema & DX.)*

**Definition of done:**

- [ ] Read replicas / read pools com load-balancing; métricas exportáveis via Prometheus/OpenTelemetry.
- [ ] Index advisor + autovacuum adaptativo + query insights disponíveis.
- [ ] MCP server para acesso seguro de agentes + ao menos uma integração de framework + caminho de **migração a partir de AlloyDB** (anti-lock-in — alimenta a métrica north-star).

**Dependencies:** M5 (deploy/operação); M2 (IA); M6 (analytics) para o conjunto completo.

**Top risks:**

1. Escopo amplo (merge de dois marcos) — priorizar sub-fatias e não inflar.
2. MCP/integrações dependerem de specs externas em movimento.

## Revision protocol

This roadmap is a living document but NOT a freeform scratchpad. To modify:

- **Marking progress:** flip the checkbox in the milestone header. No commit message ceremony required.
- **Adjusting a milestone's DoD:** edit in place, note the date in `CHANGELOG.md`.
- **Adding a milestone post-M8:** the project has outgrown its initial scope — use `/roadmap-feature` to append M9+ without renumbering, or write a new roadmap revision (e.g. `ROADMAP-v2.md`).
- **Removing a milestone:** mark it `~~M3 — [-] {name} (cancelled YYYY-MM-DD — reason)~~` rather than deleting. The history matters.
