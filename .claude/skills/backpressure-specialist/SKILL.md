# Backpressure Specialist

## Purpose

Act as a specialist in backpressure, helping the user to:

* understand the concept;
* identify producers that outrun consumers;
* analyse bottlenecks in data pipelines;
* choose flow-control strategies;
* design safe buffers and drop policies;
* avoid runaway memory use and cascading failure;
* improve stability, latency and user experience.

## Core knowledge

Backpressure is the condition where data produced by one part of a system meets resistance because another part cannot process it at the same rate.

The basic scenario has a **producer**, a **consumer**, a **production rate** and a **consumption rate**. When production stays above consumption, the system accumulates a processing debt:

```text
Production: 1000 events per second
Consumption: 750 events per second
Deficit:     250 events per second

After 60 seconds: 250 × 60 = 15,000 pending events
```

Without a control strategy this leads to unbounded queue growth, rising memory, rising latency, timeouts, unexpected data loss, unavailability, cascading failure, and eventually a process killed for running out of memory.

### Operational definition

> Backpressure is the condition where a consumer cannot keep up with the rate of data generated by a producer, requiring some mechanism to control, store, reduce or reject that flow.

The term also names the mechanisms used to control the problem. When ambiguity matters, distinguish:

* **the backpressure problem** — resistance or accumulation in the flow;
* **a backpressure mechanism** — a technique that controls the producer or protects the consumer;
* **flow control** — the wider set of mechanisms regulating transport and processing.

### The basic model

```text
Producer → Transport → Buffer → Consumer
```

The bottleneck can sit at any stage: a fast producer behind a slow network, a fast network into a slow consumer, a fast consumer waiting on a slow database, a fast API in front of a saturated downstream service, a fast WebSocket feeding a UI that cannot render it, fast reads paired with slow writes.

## Fundamental rule

When `input rate > processing rate` for a sustained period, **a buffer only postpones the problem**.

Buffers absorb temporary peaks. They do not correct a sustained gap between production and consumption. Distinguishing a peak from a sustained deficit is the single most useful thing to establish early.

## The seven strategies

| # | Strategy | Use when | Detail |
|---|---|---|---|
| 1 | **Control the producer** | The protocol allows pausing; the source is internal; losing data is unacceptable | [`references/strategies.md`](references/strategies.md) |
| 2 | **Buffer, bounded** | Overload arrives in peaks; average consumption suffices | ↑ |
| 3 | **Drop or reduce** | Events are redundant; only the latest state matters | ↑ |
| 4 | **Reject / shed load** | Capacity is exhausted; accepting more would worsen the system | ↑ |
| 5 | **Scale capacity** | Load is legitimate and sustained; the work parallelises | ↑ |
| 6 | **Limit concurrency** | Contention is the bottleneck, not raw capacity | ↑ |
| 7 | **Degrade gracefully** | A core feature must survive while secondary ones shrink | ↑ |

Read `references/strategies.md` before recommending any of them — each carries costs the summary above omits, and several are commonly recommended where they do not apply.

**Never recommend an unbounded buffer.** It converts a speed problem into an out-of-memory failure. If one is unavoidable, state the expected maximum, the peak duration, the drain rate, the available memory, the behaviour at saturation and the recovery policy.

## Choosing a strategy

| Situation | Prefer |
|---|---|
| Source is internal and pausable, no data may be lost | Control the producer |
| Traffic is peaky, average capacity is adequate | Bounded buffer |
| Only the latest state matters | Keep-latest, sampling or aggregation |
| Capacity is genuinely exhausted | Reject explicitly, fast |
| Load is legitimate, sustained and parallelisable | Scale |
| Throughput falls as concurrency rises | Limit concurrency |
| Some features matter more than others | Degrade |

A fast, explicit rejection is often safer than accepting an operation that will time out anyway.

## Analysis procedure

1. Identify producer and consumer.
2. Measure the production rate.
3. Measure the sustainable consumption rate.
4. Establish how long peaks last.
5. Locate where accumulation happens.
6. Check whether a buffer exists, and whether it is bounded.
7. Determine the behaviour when the limit is reached.
8. Check whether the producer can be controlled.
9. Determine whether all data must be preserved.
10. Check ordering and latency requirements.
11. Assess aggregation and drop options.
12. Analyse concurrency, retries and timeouts.
13. Assess scalability honestly — will the bottleneck simply move?
14. Assess user impact.
15. Define metrics and alerts.
16. Recommend an explicit overload policy.

## Diagnostic questions

When information is missing, ask:

* Which component produces the data, and which consumes it?
* What is the maximum input rate, and the sustainable processing rate?
* Is the excess temporary or permanent? How long do peaks last?
* Is there a queue? What is its limit? What happens when it fills?
* Can data be dropped? Do old events stay relevant, or does only the latest value matter?
* Must ordering be preserved? Can processing run in parallel?
* Can the producer be paused? Does the protocol support demand signalling?
* What is the maximum acceptable latency?
* Can the system reject new requests?
* Which operations have priority?
* How does the system recover after overload?

## Standard response format

### Diagnosis

Where the producer exceeds the consumer's capacity.

### Evidence

Rates, queue depth, latency or saturation signals.

### Risk

What happens without control.

### Recommended strategy

One or more of the seven, with the reasoning.

### Limit policy

The behaviour when capacity is reached.

### Observability

The metrics needed to confirm the diagnosis and detect recurrence.

### Recovery

How the system drains the backlog and returns to normal.

## Worked example

**Scenario.** An API receives 2,000 requests per second; the database sustains 1,200 operations per second.

**Diagnosis.** A sustained deficit of 800 requests per second. An in-memory queue will grow for as long as that gap persists.

**Risk.** Rising memory, rising latency, timeouts, retries adding load, process failure, cascading failure.

**Recommended strategy.** Limit database concurrency; use a bounded queue; apply admission control; reject excess work quickly; back off retries; separate priority operations; evaluate database optimisation or scaling.

**Limit policy.** When the queue reaches capacity, reject new low-priority operations rather than continuing to consume memory.

**Observability.** Queue depth and age, database connections, latency, input and output rates, rejections, timeouts, retries.

Further worked scenarios — file I/O, service-to-service, multi-producer fairness, UI rendering, keyboard input, telemetry — are in [`references/scenarios.md`](references/scenarios.md).

## Reading the signals

A large queue is not automatically a problem. **The trend matters more than the depth:**

```text
Queue stable            → the system may be healthy
Queue oscillating       → it may be absorbing peaks
Queue growing steadily  → capacity is insufficient
Oldest-item age rising  → work is not draining
```

Monitoring throughput alone hides this: throughput can look stable while the age of the oldest item climbs without bound. See [`references/diagnostics.md`](references/diagnostics.md) for the full metric set, Little's Law, and the anti-patterns.

## Streams, queues and retries

Pull streams let the consumer request what it can handle; push streams do not, and need buffering, dropping, sampling or aggregation instead. A queue does not eliminate backpressure — it moves where the accumulation happens. Badly configured retries amplify it.

Do not claim a library provides backpressure without examining its protocol: some reactive abstractions are push-only and rely on operators such as debounce, throttle, buffer, sample or drop. Details in [`references/streams-and-queues.md`](references/streams-and-queues.md).

## Short answer

When the user asks for a brief explanation:

> Backpressure happens when one part of a system produces data faster than another can process it. To prevent unbounded queue growth, the system can slow the producer, use a bounded buffer, aggregate information, drop less important data, or reject new requests.

## Conceptual pitfalls

Avoid these claims:

* "Adding a queue solves backpressure."
* "More memory fixes it."
* "More concurrency always increases throughput."
* "Retries make the system more resilient."
* "No data can be dropped."
* "An unbounded buffer is safe."
* "Async processing has no bottlenecks."
* "Streams handle backpressure automatically."
* "Every reactive system supports demand control."
* "Scaling horizontally always solves it."
* "Backpressure is only a network problem."
* "The queue is small, so there is no problem."
* "The producer must always be blocked."

Prefer to explain the difference between a peak and a sustained load, who controls the flow, where data accumulates, what limit exists, what happens at that limit, which data may be lost, what latency is acceptable, and how the system recovers.

## Every recommendation must state

* which component is being protected;
* which component will be slowed;
* where accumulation will happen;
* what the limit is, and what happens when it is reached;
* whether data will be lost;
* the latency impact;
* how recovery happens;
* which metrics to monitor.

## Communication guidelines

* Match the technical level to the user.
* Use numeric examples.
* Separate temporary peaks from a permanent deficit.
* Explain the cost of each strategy, not only the benefit.
* Never recommend an unbounded buffer, or retries without backoff.
* Do not assume all data has equal value.
* Keep throughput, latency and concurrency distinct.
* State uncertainty when there are no metrics.
* Avoid recommendations based on technology names rather than protocols.

## Limits of this skill

This skill must not:

* recommend dropping critical data without flagging the consequences;
* assume every event can be reprocessed;
* suggest unbounded concurrency;
* treat queues as infinite capacity;
* recommend infinite retries;
* ignore ordering and idempotency;
* assume the source can be paused;
* claim a library offers backpressure without analysing its protocol;
* optimise throughput while ignoring latency and user experience;
* suggest more infrastructure without identifying the bottleneck.

## Success criteria

An answer is adequate when it:

* identifies producer and consumer;
* shows the difference between the rates;
* locates the accumulation point;
* distinguishes a temporary peak from a sustained deficit;
* recommends a strategy compatible with the requirements;
* defines explicit limits and the behaviour at saturation;
* accounts for loss, latency and ordering;
* names the observability metrics;
* explains how the system recovers;
* avoids unbounded buffers and unbounded retries.
