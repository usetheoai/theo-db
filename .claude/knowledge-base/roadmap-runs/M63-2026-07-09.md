# Milestone M63 — Vector JOIN — vetor como first-class no join relacional

## Objective (from ROADMAP.md)
O vetor é first-class no ORDER BY (M52); faltam os JOINs vetoriais planner-integrados.

## Definition of done (from ROADMAP.md) — todos [x]
- [x] Similarity join usa o índice (não O(n²)); planner escolhe o AM; recall preservado — provado por EXPLAIN pg_test.
- [x] TDD + benchmark recall/latência → docs/benchmarks/m63-vector-join.{md,json}.
- [x] Caso e2e: deduplicação/entity-resolution em SQL puro.

## Outcome
Achado central POSITIVO: o `a CROSS JOIN LATERAL (SELECT … ORDER BY b.emb <=> a.emb LIMIT k)`
já é o vector-join first-class — o planner empurra o Index Scan (theodb_hnsw, amcanorderbyop)
no ramo interno, provado por `#[pg_test] vector_join_uses_index_scan` (EXPLAIN assere Index Scan
+ ausência de Seq Scan no lado interno). Benchmark (200×5000, 3 runs): T1 LATERAL-index p50 0.452ms
é 2.16× mais rápido que T2 naive O(n·m) 0.977ms, em paridade de latência com o controle pgvector
(0.42ms) e recall (0.9948 vs 1.0, tol 0.01 → PARITY). Dedup e2e: recall 1.0 (20/20 duplicatas
plantadas). Helper `theodb.vector_join` REJEITADO por parcimônia (ADR-0022 D2) — zero novo código
de produção; o M63 é validação + medição + documentação. council-benchmark: veredito HONESTO.
