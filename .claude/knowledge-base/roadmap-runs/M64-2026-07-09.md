# Milestone M64 — RAG-sobre-SQL unificado (a query única)

## Objective (from ROADMAP.md)
O "one query" story: filtro relacional + retrieval vetorial + (opcional) agregação columnar numa query só.

## Definition of done (from ROADMAP.md) — todos [x]
- [x] Query de referência planner-integrada, recall+latência medidos — Path 1 (row-store) provado por pg_test + benchmark; Path 2 columnar honesto (2 statements, ADR-0023).
- [x] Doc do padrão RAG-nativo + benchmark.
- [x] Veredito honesto vs app-layer.

## Outcome
Achado central: as peças de retrieval (M52/M53/M63) já são planner-integradas — o M64 é composição+medição+documentação
(zero código de produção novo, rung-1 parsimony, precedente ADR-0022). O DoD pedia "agregação columnar
planner-integrada", que é ESTRUTURALMENTE inalcançável (pg_duckdb proíbe DuckDB em função ADR-0021; row-store +
Parquet são 2 engines com 2 planners) — ADR-0023 corrige a premissa: Path 1 (uma SQL row-store real) + Path 2
(columnar = 2 statements, padrão M62). Provado por 2 #[pg_test] GREEN (recall preservado + read-your-writes) no
stack real (theodb_rs+vector+vectorscale+theodb via CASCADE). Benchmark "1 SQL vs N app-calls": A_unified 1
round-trip 6.721ms vs B_app_layer 2 round-trips 7.284ms, recall jaccard 1.0 — vitória estrutural round_trips
(1 vs 2, amplifica sobre rede), co-located ~8%. Straw-man do braço B corrigido (PRIMARY KEY). Review do CTO
(6 pontos de precisão editorial) aplicado ao ADR. council-benchmark: HONESTO.
