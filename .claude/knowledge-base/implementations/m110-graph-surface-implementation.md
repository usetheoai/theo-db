# M110 — in-DB graph extraction surface — implementation summary

## Outcome

Shipped `ai.extract_entities` / `ai.extract_graph` (heuristic-default + `use_llm` opt-in) and idempotent
`theodb.graph_upsert` into CSR-shaped `theodb.graph_nodes`/`graph_edges`, all in a new module
`theodb_rs/src/graph_extract.rs`. The heuristic is a **byte-identical Rust port** of theo-rag's
`graph-extractor.ts`; the upsert mirrors `graph-store.ts` (`ON CONFLICT … +=`).

## The gate — recall non-regression BY CONSTRUCTION

theo-rag's own graph-quality baseline IS the heuristic. So **cross-language parity (100% coverage) + E2E
set-hash equality** prove the in-DB graph == theo-rag's graph and the traversal == theo-rag's traversal →
downstream retrieval recall is non-regressed by construction (blueprint ADR-2), without a separate QA eval.
Golden values were generated by running theo-rag's real compiled `graph-extractor.js` on the fixtures (not
hand-traced).

## Measured (`docs/benchmarks/m110-extraction.{md,json}`)

- extraction 1537 chunks/sec (heuristic, pure in-backend Rust), upsert 108.7 chunks/sec, 5000 edges, parity 100%.

## Honest boundary

- Heuristic recall < LLM (multi-hop/global) — gate is non-regression vs theo-rag's heuristic (parity by
  construction), not absolute quality. `use_llm` path is wired + parser-tested + fail-soft; its absolute
  multi-hop quality gain is a separate measured study (not required to ship the heuristic surface).
- `graph_build` scopes over the whole edge relation → per-workspace CSR needs a filtered view (follow-on); table
  tenant isolation itself is proven.
- LLM path not hermetically testable for the happy path (the `'parity'` test model returns yes/no, not tuples) →
  parser tested as a pure function; fail-soft + bounded-call proven under `'parity'`.
