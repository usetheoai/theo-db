## Release notes

### Fixed
- **`theodb_columnar_agg` CustomScan: EXPLAIN no longer hangs on `ORDER BY <aggregate>` (closes #135).** The node
  published a self-referential `custom_scan_tlist` (`Var(INDEX_VAR, i)`), so `ruleutils.c::resolve_special_varno`
  recursed forever when a `Sort` above it keyed on the aggregate output. `statement_timeout` could not interrupt it
  (plan *printing*, not planning) — only a server restart could.
- `custom_scan_tlist` now carries deparse-safe expressions, **descriptor-equal** to the list it replaces (it is also
  the node's runtime scan `TupleDesc`), and the construction is **fail-closed** — an inconsistent list declines the
  swap to the native plan.

### The #135 diagnosis was falsified (live gdb backtrace)
Not a planner hang, not O(cols^2), not width/TEXT-related — the query always EXECUTED correctly (0.537 s). The
trigger is `ORDER BY <aggregate>` + EXPLAIN.

### Measured (shipped binary; self-hosted, NOT canonical hardware; n=100k)
- 43-query ClickBench EXPLAIN sweep, pushdown ON: hangs **2 -> 0**, max **60 ms** (Q16 31 ms, Q33 30 ms, both
  engaging the CustomScan). Gate: `scripts/m131_sweep.sh` exits non-zero on any hang.
- Accelerated vs storage-path control, same box: **byte-identical 43/43** in both; **1.90x** full-suite hot geomean;
  **24.8x** across the six queries the pushdown touches (**20.7x** excluding q6, served by the pre-existing zone-map
  fast-path).
- Disclosed: single suite run per configuration; +-21% noise floor across the 37 untouched queries. Internal A/B of
  TheoDB against itself — NOT a competitive claim, NOT a leaderboard result.

Review: 0 BLOCKER / 0 HIGH from council-rust-pgrx + council-benchmark; 1 HIGH + 8 MEDIUM/LOW raised and all
resolved, then re-verified on the rebuilt binary.
