## Release notes

### Added
- M36 Phase 1 — otimização do scan do índice: heap min lazy top-K (`am/scan.rs`). O gate measurement-first do M36
  (`THEODB_SCAN_PROFILE`) falsificou a premissa original ("quantizar a distância"): distância ~15% do custo; os
  gargalos são `reads` (~44%) e `sort` (~38%). Phase 1 substitui o `results.sort_by` O(C·log C) de TODOS os
  candidatos por um heap min lazy (heapify O(C) + pop O(log C) = O(C+k·log C)). Top-K byte-idêntico → recall
  inalterado (por construção + pg_test de ordering + 61 testes de coexistência). Fase sort caiu ~10–13×
  (profiler); end-to-end ~1.5× band (mean±std, recall idêntico), Amdahl-limitado pelo `reads`. Evidência:
  `docs/benchmarks/m36-scan-optimization.{md,json}`.

### Changed
- Roadmap: M36 re-escopado (só Phase 1/heap) + M38 criado (quantização de I/O, o gargalo `reads`, recall-risco) —
  ADR-2: medir o heap de recall-zero-risco antes de comprometer o risco maior.

## Outcome

O measurement-first funcionou como projetado: falsificou a premissa original do M36 antes de qualquer código,
re-escopando o milestone para o gargalo `sort` real. Phase 1 entrega ~1.5× de speedup de scan a recall idêntico
(zero risco), honestamente NÃO fechando o gap de 25× do ScaNN sozinho. O `reads` (~44%, o gargalo maior) continua
no M38. M36+M38 juntos atacam ~80% do custo de scan medido.
